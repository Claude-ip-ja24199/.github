<p>人一走，账号就乱，这是很多小团队的通病。乱的根源通常不是没交接密码，而是交接之前没人做过决策：这条出口算谁的、环境整体搬还是留下、密钥切到什么程度。三个决策没定，接手人只能靠猜，猜错一次就得整批重配，前面攒的地址连续性全丢。这篇把交接拆成三项决策加两份清单，每项给出判断依据和代价对比，适用于采用原生家宽出口、账号与线路长期绑定的团队，节点从确定离职那天算起到接手满一周。</p>

<h2>一、交接要先做三个判断，不然换人等于重建</h2>
<p>很多人是先动手迁环境，遇到问题再回头讨论归属，结果迁到一半发现出口不该跟着人走，前面做的工作全废。顺序应该是先定归属，再定迁移范围，最后切权限。</p>
<h3>三个判断的顺序</h3>
<p>第一，出口归属：地址是跟着账号，还是跟着操作人。第二，环境范围：整个浏览器与存储搬走，还是只换登录的人。第三，权限切分：哪些密钥必须换、哪些可以留、换的时点放在哪。三者的依赖关系是单向的，前一项没定，后一项的答案就不唯一。</p>
<h3>判断错了的代价</h3>
<p>归属搞错，会出现「账号换人了但地址跟着走了」的情况，新操作人一登录就是陌生地址，验证接踵而来。范围搞错，会把本来稳定的存储目录重建，等于给账号换了个身份。权限切错，轻则接手人干不了活，重则离职的人还能回来看。</p>

<h2>二、判断一：出口跟着账号走，还是跟着人走</h2>
<p>这个判断取决于你的账号是按人划分还是按业务划分。两种模型都合理，混着用才出问题。</p>
<h3>两种模型的适用</h3>
<p>按人划分：一个人负责一批账号，出口跟着人走，人走了这批账号连地址一起交给下一个人。这种方式交接简单，但账号的环境和历史绑在个人身上，人走等于经验走。按业务划分：账号按业务线固定，出口跟着账号走不动，操作人只是轮换。这种方式抗人员流动，代价是新接手人需要适应期。</p>
<h3>怎么落成一张表</h3>
<p>不管选哪种，都要有一张绑定表，三列就够：账号、出口地址、责任人。离职当天把责任人一列改掉，其余两列一个字都不动。这张表的价值在于，它让「不整批重配」变成一句可执行的话——只要地址那列没被改动，环境就是连续的。</p>

<h2>三、判断二：环境整体迁移，还是只换操作人</h2>
<p>这一项最容易被情绪左右。有人觉得让新人用老人的机器不放心，一律重装；也有人图快，直接给个账号密码就算交接。两种极端都会带来额外成本。</p>
<h3>整体迁移怎么做</h3>
<p>原设备如果留在团队内、且没有其他人共用，最省事的做法是把设备的系统账户改掉、把浏览器配置与存储目录原样保留、只更换登录凭据。这样出口、时区、指纹、存储全部连续，账号在服务端看来几乎没有变化。前提是这台设备从今往后只服务这一个接手人。</p>
<h3>只换操作人的风险</h3>
<p>如果设备要共用，就必须走整体迁移：把每个账号的存储目录打包，迁到接手人自己的隔离环境里，同时保证出口地址不变。风险点在于时区与地理位置的自洽——目录迁过去了，但新机器的系统时区如果没改，就会出现「地址在日本、系统时钟在别处」的矛盾。</p>

<h2>四、判断三：密钥与权限怎么切，切到什么程度</h2>
<p>账号能登进去，不等于权限交干净了。API 密钥、支付方式、管理后台、以及各种二次验证的绑定手机或邮箱，都要在这一步处理。</p>
<h3>密钥分级的做法</h3>
<p>分三级：一级是能直接产生费用或改动账号设置的（支付、管理后台、主密钥），必须全部轮换；二级是只读或受限调用的（统计、日志查询），可以保留但要在审计日志里确认没有异常调用；三级是临时凭据，直接作废。分级的好处是不用一刀切，既保证安全又不至于让接手人第一周什么都干不了。</p>
<h3>回收动作要留痕</h3>
<p>每完成一项回收，记一行：时间、项目、操作人、验证方式。这不是形式主义，因为半年后如果有人问「当时支付方式到底换了没有」，只有这行记录能回答。</p>

<h2>五、交接当天到一周内的执行清单</h2>
<p>决策定完，剩下的就是按顺序执行。顺序错了会返工，尤其是先切权限后迁环境这种。</p>
<h3>交接当天五项</h3>
<p>一是确认绑定表已改责任人；二是确认出口地址未变动，并在台账里注明「本次交接不调整出口」；三是把存储目录备份一份留档，防止迁移出错；四是轮换一级密钥；五是让接手人用低强度操作跑一遍主流程，确认能通。</p>
<h3>一周内三项复核</h3>
<p>第一天看有没有验证提示；第三天看常用功能是否齐全；第七天看操作时段是否已形成新的规律。三项都过，交接才算完成。如果第一天就出现验证，别急着改配置，先核对是不是接手人用了自己的设备或自己的网络。</p>

<h2>常见问答</h2>
<h3>离职的人知道所有账号密码，要不要全部改一遍？</h3>
<p>答：按权限分级处理。能产生费用、能改设置、能看客户数据的三类必须改；只读统计类的可以保留，但要查一遍最近的调用记录。全部改一遍虽然彻底，但会让接手人第一周忙于重置，反而增加出错机会。</p>
<h3>接手人用自己的笔记本，出口会不会变？</h3>
<p>答：会。出口取决于走哪条线路，不取决于设备。只要把隧道配置原样迁过去、并且绑定关系没动，出口地址就不变。真正会变的是浏览器侧的特征，所以存储目录要一起迁。</p>
<h3>原设备还能不能给别人用？</h3>
<p>答：可以，但必须先把该账号的存储目录迁出并清除本地残留，再交给下一个人。共用一台设备跑多个账号，等于把地址隔离的效果抵消掉，这一点在人员紧张时最容易被忽略。</p>
<h3>交接期间要不要停掉账号的自动化任务？</h3>
<p>答：建议停 24 小时。迁移过程中任务还在跑，容易在配置切换的瞬间产生异常请求，事后很难判断是迁移导致还是任务本身的问题。停一天的成本，远低于排查两天的成本。</p>

<h2>合规提示</h2>
<p>交接涉及个人信息与账号凭据，请按最小必要原则处理：只移交工作必需的权限，离职人员的个人凭据应及时回收，避免长期留存。</p>
<p>账号的使用主体、注册信息应与实际一致，平台要求补充材料或重新验证时应如实配合，不得由他人代为通过身份核验。</p>
